# Ограничения и возможные улучшения

## Ограничения

- **Сверка чисел не ловит всё.** Проверяется, что число есть во входных данных, но не то, что оно стоит в правильном месте. Если модель напишет «температура до 150 °C» про окружающую среду, хотя 150 относится к измеряемой среде, проверка это пропустит. Не ловятся и числа словами («два порога»).
- **Нечисловые выдумки ловит только промпт.** Материал, тип сенсора или назначение, которых нет во входе, код не распознаёт. Такие ошибки остаются на вычитке контент-менеджера.
- **Типовые характеристики заданы вручную** для четырёх видов приборов: манометры, газоанализаторы и сигнализаторы газа, датчики давления, термометры и термопреобразователи. Для остальных видов пробелы ищет только модель. Сопоставление идёт по подстрокам в названиях характеристик и может ошибиться на нестандартных названиях.
- **Длина считается в символах вместе с пробелами.** Если в CMS другой способ подсчёта, границы нужно поправить в `checks.py`.
- **Одна попытка исправления.** Если модель дважды не уложилась в требования, карточка возвращается со статусом `needs_review` и списком нарушений. Число попыток настраивается (`LLM_FIX_ATTEMPTS`), но каждая попытка стоит денег и времени.
- **Сборщик входа из фида завязан на вёрстку сайта** (блоки `#description` и `#specifications`). При изменении вёрстки его придётся поправить. Таблицы и списки из описания переносятся упрощённо.
- **Один провайдер.** Реализован только Claude. Другой провайдер подключается классом с методом `complete()`, но сейчас его нет.
- **Нет пакетной обработки и хранения.** Каждый товар обрабатывается отдельным запросом, результаты не сохраняются, история правок не ведётся. Для прототипа это осознанно (в задании CMS и база не требуются).
- **Веб-форма без авторизации** и рассчитана на локальный запуск.

## Что можно улучшить

1. **Проверка привязки чисел к характеристикам.** Для каждого числа в тексте искать ближайшую единицу измерения и сверять пару «число и единица» с парами из входа. Это закроет часть случаев, когда число верное, но относится к другому параметру.
2. **Вторая модель как проверяющий.** Отдельный короткий запрос: «найди в тексте утверждения, которых нет во входных данных». Дешёвая модель с низким effort, результат идёт в предупреждения.
3. **Справочник типовых характеристик из каталога.** Собрать по категориям фида самые частые названия характеристик и использовать их вместо ручного списка. Заодно нормализовать названия («Класс точности», «Кл. точности», «Точность»).
4. **Набор эталонных карточек и регрессионная оценка.** 30–50 товаров из разных категорий с ручной разметкой: сколько выдуманных значений, сколько пробелов найдено, сколько карточек прошло проверки с первой попытки. Без этого нельзя честно сравнить промпты и модели.
5. **Пакетный режим.** Обработка категории фида целиком через Message Batches API (дешевле вдвое), кэширование системного промпта, выгрузка в CSV или формат импорта CMS.
6. **Правила стиля магазина.** Шаблон заголовка, запрещённые слова, обязательные блоки описания вынести в конфиг, чтобы контент-отдел менял их без правки кода.
7. **Учёт модификаций.** У многих товаров в фиде десятки модификаций одной модели (например, разные диапазоны манометра). Можно генерировать общий текст на модель и короткие отличия на модификацию.
8. **Поисковые запросы по данным.** Сейчас запросы предлагает модель по смыслу. Их можно сверять с Wordstat или поисковыми подсказками, чтобы выбирать запросы с реальным спросом.
