# Промпты и принятые решения

## Модель и вызов

- Провайдер: Anthropic, официальный Python SDK `anthropic`. Модель по умолчанию `claude-sonnet-5-5`, меняется через `LLM_MODEL`.
- Ответ запрашивается через structured outputs (`output_config.format` с JSON-схемой). Модель физически не может вернуть текст вне схемы, поэтому не нужно вытаскивать JSON из ответа регулярками. Схема лежит в `card_gen/prompts.py` (`DRAFT_SCHEMA`), ответ дополнительно проверяется pydantic-моделью `LLMDraft`.
- Глубина рассуждений `effort=medium`: задача короткая, но требует внимательности к данным. Меняется через `LLM_EFFORT`.
- Включён серверный fallback Anthropic (`fallbacks: "default"`): если модель отказывается отвечать, API само повторяет запрос на резервной модели. Выключается `LLM_FALLBACKS=off`.
- Повторы при 429, 5xx и обрыве связи делает SDK (`LLM_MAX_RETRIES`). Все остальные ошибки API превращаются в понятные сообщения: неверный ключ, нет доступа к модели, лимит, таймаут, нет связи, отказ модели, обрезанный ответ.

## Системный промпт

Полный текст в `card_gen/prompts.py` (`SYSTEM_PROMPT`). Как он устроен:

1. **Контекст.** Кто читает карточку (инженеры, снабженцы, монтажники) и что черновик потом вычитывает контент-менеджер. Отсюда приоритет: точность важнее красоты.
2. **Один источник фактов.** Данные товара передаются в теге `<product>` и прямо названы данными, а не инструкциями. Это защита от случайных или намеренных команд в тексте описания.
3. **Запрет на выдумку с конкретикой.** Вместо общего «не выдумывай» перечислено, что именно нельзя добавлять: числа, единицы, материалы, стандарты, сертификаты, номера в Госреестре, интерфейсы, питание. Отдельно запрещены пересчёт единиц и округление, потому что модель охотно пишет «10 кгс/см² (≈1 МПа)», а это новое число. Запрещены обещания цены, наличия, поверки и доставки.
4. **Что делать при нехватке данных.** Не писать значение и вынести вопрос в `data_issues`. Модели дан понятный выход, поэтому ей не нужно «дотягивать» текст догадками.
5. **Требования к каждому полю.** Для SEO-описания кроме диапазона 800–1200 символов дан ориентир в словах (130–150), потому что модели плохо считают символы и хорошо держат объём в словах.
6. **Характеристики.** Модель не переписывает значения, а только выбирает названия ключевых характеристик (`key_spec_keys`) символ в символ. Значения подставляет код.
7. **Извлечение из названия и описания.** Если характеристика есть в названии или описании, но не в `specs`, модель возвращает её в `extracted_specs` с точной цитатой из источника. Код проверяет, что цитата действительно есть в тексте, а числа значения есть в цитате.
8. **Что уточнить.** Модель отмечает противоречия между полями и неоднозначные значения. Это то, что код сам найти не может.

Пример промпта не завязан на конкретные товары из `examples/`, чтобы не подгонять результат под два примера.

## Пользовательский промпт

Строится в `build_user_prompt`: JSON товара в теге `<product>` и, если код нашёл пробелы, подсказка вида «для прибора типа манометр в specs не найдено: Диапазон измерений; если значение есть в названии, вынеси его с цитатой, если нет, отметь в data_issues». Служебные поля (`url`, `sku`) модели не передаются.

## Промпт исправления

Если черновик не прошёл проверки, модель получает исходные данные, свой прошлый черновик в теге `<previous_draft>` и список нарушений с цифрами: «SEO-описание 1340 символов, нужно 800–1200: сократите примерно на 240 символов», «в SEO-заголовке есть числа, которых нет во входных данных: 65». Повтор делается отдельным запросом, а не продолжением диалога: так проще и дешевле, а контекст всё равно целиком в промпте. Из двух попыток берётся черновик с меньшим числом нарушений.

## Почему защита от выдумки сделана кодом, а не только промптом

Промпт снижает вероятность ошибки, но не гарантирует её отсутствие. Поэтому проверки, которые можно сделать кодом, сделаны кодом:

- **Характеристики из входа.** Таблица характеристик собирается из входных данных, модель на значения не влияет. Если модель назвала характеристику, которой нет во входе, она отбрасывается с предупреждением.
- **Сверка чисел.** Из SEO-заголовка, описания, запросов и блока для менеджера извлекаются все числа и сравниваются с числами входных данных (с учётом записи `1,5` и `1.5`, дробей вида `½`). Любое лишнее число считается нарушением: модель получает его на исправление, а если оно осталось, оно попадает в предупреждения карточки.
- **Цитаты.** Значения, найденные в названии или описании, принимаются только если цитата дословно есть в источнике.
- **«Данных нет».** Для каждого вида прибора задан короткий список типовых характеристик. Если их нет во входе и модель не нашла их с цитатой, в таблице стоит «данных нет», а в «Что уточнить» появляется замечание.
- **Длины и количество.** Заголовок до 70 символов, описание 800–1200, запросов 3–5 проверяются кодом, а не доверяются модели.

## Прочие решения

- **Отказ без вызова модели.** Если нет названия или нет ни характеристик, ни описания, сервис сразу возвращает список пробелов. Текст без фактов получился бы общим и бесполезным, а запрос стоил бы денег.
- **Статус карточки** (`ready`, `needs_data`, `needs_review`) помогает контент-менеджеру понять, что делать: публиковать после вычитки, запросить данные или поправить текст.
- **Провайдер за интерфейсом.** Генератор зависит только от протокола `LLMClient` с одним методом `complete()`. Благодаря этому тесты работают без ключа, а другого провайдера можно подключить одним классом.
- **Входные данные из фида.** В YML-фиде магазина нет характеристик и описаний, поэтому `scripts/build_input.py` берёт их со страницы товара. Подзаголовки групп в таблице характеристик (например, «Диапазон рабочих температур, °C») переносятся в названия строк, чтобы «Окружающая среда: −60…+60» не потеряла смысл.
