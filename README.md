# Черновики карточек товаров для магазина КИП

Прототип сервиса для тестового задания «AI-помощник для подготовки товарных описаний» (Союз-Прибор).

На вход: JSON с названием, производителем, характеристиками и описанием прибора. На выходе черновик карточки:

- SEO-заголовок до 70 символов;
- SEO-описание на 800–1200 символов;
- список ключевых характеристик, значения в котором берутся из входных данных без изменений;
- 3–5 поисковых запросов;
- блок для менеджера: кому подходит прибор, какие задачи решает, аргументы для клиента;
- список «Что уточнить»: каких данных не хватает, где данные противоречат друг другу;
- результат автоматических проверок и статус карточки.

Результат отдаётся в Markdown (читать и копировать) и в JSON (загружать в CMS). Работать можно через командную строку или через веб-форму.

## Установка

Нужен Python 3.10 или новее (проверено на 3.13).

```bash
python3 -m venv .venv
source .venv/bin/activate
pip install -r requirements-dev.txt     # для работы без тестов хватит requirements.txt
cp .env.example .env                    # и впишите ANTHROPIC_API_KEY
```

Ключ читается только из переменной окружения `ANTHROPIC_API_KEY` или из файла `.env` в папке, откуда запускается сервис. Файл `.env` добавлен в `.gitignore`, в коде ключа нет.

Остальные настройки необязательные, они перечислены в `.env.example`:

| Переменная | По умолчанию | Что делает |
|---|---|---|
| `LLM_MODEL` | `claude-sonnet-5-5` | модель Claude |
| `LLM_EFFORT` | `medium` | глубина рассуждений модели: `low`, `medium`, `high` |
| `LLM_TIMEOUT` | `120` | таймаут одного запроса, секунд |
| `LLM_MAX_RETRIES` | `2` | повторы SDK при 429, 5xx и обрыве связи |
| `LLM_FIX_ATTEMPTS` | `1` | сколько раз перегенерировать черновик, если он не прошёл проверки |
| `LLM_FALLBACKS` | `default` | серверный fallback Anthropic, если модель отказалась отвечать; `off` выключает |

## Запуск

### Командная строка

```bash
# карточка в Markdown в консоль
python -m card_gen examples/manometer_tm510r_m2.json

# в JSON
python -m card_gen examples/gas_detector_dz1_co.json --format json

# несколько товаров сразу, результат в файлы <имя>.md и <имя>.json
python -m card_gen examples/*.json --out-dir examples/out

# только проверить входные данные, без запроса к модели (ключ не нужен)
python -m card_gen examples/manometer_tm510r_m2.json --check-only

# JSON из stdin
cat product.json | python -m card_gen -
```

Коды выхода: `0` успех, `2` ошибка во входных данных или данных не хватает, `3` нет ключа или неверная настройка, `4` ошибка API модели.

### Веб-форма

```bash
uvicorn card_gen.web:app --reload
```

Откройте http://127.0.0.1:8000. Данные можно ввести по полям (характеристики по одной в строке, «название: значение») или вставить JSON. Кнопки с названиями товаров подставляют примеры из `examples/`. «Проверить данные» показывает пробелы во входе без обращения к модели. У SEO-заголовка и SEO-описания есть счётчики символов и кнопки «Копировать», внизу карточка целиком в Markdown или JSON.

HTTP API для интеграции:

- `POST /api/card`: тело запроса JSON товара, ответ `{"card": {...}, "markdown": "..."}`;
- `POST /api/check`: только проверка входа, ответ `{"issues": [...]}`.

Ошибки возвращаются как `{"error": "текст"}`: `400` некорректный JSON, `422` данных недостаточно (с полем `issues`), `502` ошибка модели, `503` не задан ключ.

### Тесты

```bash
pytest
```

Тесты не ходят в API: модель подменяется заглушкой. Проверяются разбор некорректного JSON, пустые поля, поиск пропущенных характеристик, отлов выдуманных чисел, повторная генерация при нарушениях, обработка ошибок API, CLI и веб-эндпоинты.

## Формат входа

```json
{
  "name": "Манометр показывающий DM 02",
  "manufacturer": "Манотомь",
  "specs": {
    "диапазон измерений": "0–1,6 МПа",
    "класс точности": "1,5"
  },
  "description": "Прибор предназначен для измерения избыточного давления..."
}
```

Обязательно только `name` и хотя бы одно из `specs` или `description`. Необязательные поля: `category` (вид прибора), `url`, `sku`. Принимаются и названия полей из YML-фида: `vendor`, `typePrefix`, `vendorCode`. Характеристики можно передать объектом, списком `{"name", "value"}` или списком строк «название: значение». HTML в описании очищается автоматически.

## Примеры: два товара из фида магазина

Оба товара взяты из YML-фида `https://www.souz-pribor.ru/yml/any/feed.xml`:

| Файл | Товар | Почему выбран |
|---|---|---|
| `examples/manometer_tm510r_m2.json` | Манометр РОСМА ТМ-510Р.00(0-10 кгс/см2)G1/2.М2 (offer 190403) | Типичный неполный ввод: диапазон измерений есть только в названии модели, в характеристиках его нет; резьба указана двумя вариантами, хотя в названии одна |
| `examples/gas_detector_dz1_co.json` | Сигнализатор загазованности ОВЕН ДЗ-1-СО (offer 74022) | Прибор другого типа с подробными характеристиками; в описании рабочая температура −40…+80 °С, а в характеристиках −20…+70 °С, модель должна это заметить, а не выбрать одно из значений |

В фиде у товаров есть только название, производитель, вид прибора и ссылка, характеристик и описаний там нет. Поэтому `scripts/build_input.py` берёт товар из фида по `offer id`, а характеристики и описание забирает со страницы товара по ссылке из фида:

```bash
curl -o feed.xml https://www.souz-pribor.ru/yml/any/feed.xml
python scripts/build_input.py --feed feed.xml --offer-id 190403 --out examples/manometer_tm510r_m2.json
python scripts/build_input.py --feed feed.xml --offer-id 74022 --out examples/gas_detector_dz1_co.json
```

Готовые карточки лежат в `examples/out/`. Пересоздать их:

```bash
./scripts/make_examples.sh
```

## Как устроено

```
card_gen/
  input_loader.py   разбор и нормализация входного JSON, понятные ошибки
  checks.py         проверки кодом: пробелы во входе, длины, числа, цитаты
  prompts.py        системный промпт, промпт исправления, JSON-схема ответа
  llm.py            клиент Claude (официальный SDK anthropic), обработка ошибок API
  generator.py      сборка карточки и повторная генерация при нарушениях
  render.py         Markdown для контент-менеджера
  web.py, static/   веб-форма и HTTP API на FastAPI
  __main__.py       командная строка
scripts/            сборка входа из фида, генерация примеров
tests/              pytest, без обращений к API
```

Порядок работы:

1. Вход разбирается и нормализуется. Некорректный JSON, неверные типы полей и пустой ввод дают понятную ошибку.
2. Код ищет пробелы: нет производителя, пустые значения, короткое описание, нет типовых для этого вида прибора характеристик (у манометра диапазон, класс точности, резьба, диаметр корпуса; у газоанализатора газ, диапазон, сенсор, питание, степень защиты). Если нет названия или нет ни характеристик, ни описания, модель не вызывается.
3. Модель получает данные и список найденных пробелов и возвращает черновик строго по JSON-схеме (structured outputs).
4. Код проверяет черновик: длины, количество запросов, числа в текстах, которых нет во входе, названия характеристик и цитаты. При нарушениях модель один раз получает черновик назад со списком проблем. Если проблемы остались, они попадают в раздел «Проверка», и карточка получает статус `needs_review`.
5. Список характеристик собирает код: значения копируются из входа, для недостающих типовых характеристик ставится «данных нет».

Статусы карточки: `ready` (проверки пройдены, вопросов к данным нет), `needs_data` (текст в порядке, но во входе есть пробелы), `needs_review` (черновик не прошёл проверки, нужна правка руками).
